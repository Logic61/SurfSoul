# 生活参数自调 · 清单（请审阅）

> 用途：让 QQ 里的 agent 通过工具**自己调整**自己的行为/生活参数（B站作息、主动冒泡、唤醒概率、目的节奏等），
> 但只开放「机会与节奏」类参数；身份、凭据、白名单、权限、预算硬上限永远只读。
> 本文是**待你审阅的开放范围清单**：每行「建议」列是本次实现采用的默认权限；你只要指出要改的行即可。
> 当前值 = 2026-11-08 真机实读；范围 = 工具层校验的硬 clamp（超出直接拒绝，不会静默写坏）。
>
> 相关：设计/运维见 [LIFE-SETTINGS.md](LIFE-SETTINGS.md)；参考实现（GitHub）surfcore-life 的 30 参数目录。
> 实现口径与参考仓库的差异在文末「相对参考仓库的优化」。

---

## 0. 先看结论

1. **建议开放 29 项**：全部是「机会 / 节奏 / 数量 / 兴趣词」类，不会放开任何账号、凭据、白名单、权限或预算硬上限。
2. **1 项建议要你审批**：`QQ 唤醒上下文字数`（直接放大每次唤醒的 token 成本）——agent 可以预览，但必须你在本机批准。
3. **建议保持只读 6 组**：token 防爆破/每日额度、目的每日上限、B站行为硬额度、模型/思考档位、记忆与遗忘规则。
4. **权限口径（最重要，请确认）**：
   - 写参数只允许在**主人本人私聊**、或**主人本人那条消息触发的回合**里发生；
   - 群友触发的回合只能读、不能改（群友转述「主人说改一下」不算授权）；
   - 主人触发的群回合里，写操作还会再过一次内部模型审批（与现有禁言/改名片等特权工具同口径）；
   - 所有修改都有预览 → 执行 → 验证 → 回滚，并落审计。

## 5.「先少一点自动模型机会。」

你说的「减少主动机会和自动浏览机会；已有预算硬闸继续约束消费」，工具层**不需要新增放开项**，用上面 4 组就能做到：

- 一次性变小：`purpose.enabled=false` + `proactive.enabled=false` + `night.maxWakesPerDay` 调低/0；
- 或调用内置意图 `fewer-model-opportunities` / `less-disturbance` / `more-solitude`，工具会生成确定的联动 patch（仍要预览+执行）；
- **预算硬闸保持只读**（见下），所以「少自动机会」能省，但 agent 不能给自己放宽额度。

## 7. 保持只读（不开放给普通接口，连预览都不给改）

| 组 | 为什么 |
|---|---|
| `socialV2.tokenGuard.*`（防爆破开关/每日唤醒上限/最小间隔/单轮发送数/每日花费上限） | 预算与外部活动硬上限；放开等于「自己给自己加零花钱」 |
| `purpose.dailyMax`（当前 4） | 每日目的硬上限；原代码 0=不限，语义含糊，保持只读 |
| `bili.limits.*`（评论 30/回复 50/搭话 15/挖矿 10/每 UP 10 分钟/每视频 60 分钟…） | B站行为授权，不是生活节奏 |
| `qq.dsh.model` / `reasoningEffort` | 可能改 DSH 全局默认，且配置值≠实际请求 |
| `memoryCard.*`（容量/注入/模糊/遗忘） | 涉及遗忘与隐私 |
| 凭据、cookie、账号身份、`allow`/`deny` 名单、模式/preset、工具审批开关、鱼群保护硬闸、系统提示词 | 安全边界，永不进生活参数接口 |

> 补充：`socialV2.tokenGuard.enabled` 真机现在是 `false`（防爆破总开关关着），这是你当前配置的现实；
> 生活参数工具不会去动它，也不会因为「想省 token」把它打开——那属于安全策略，由你决定。

## 8. 权限与操作口径（请确认）

| 场景 | 能做什么 |
|---|---|
| 主人本人私聊 | 读 + 写（预览/执行/回滚/记录观察）；写不跑模型审批 |
| 群里「主人本人那条消息」触发的回合 | 读 + 写；写操作逐次过内部模型审批（和禁言/改名片同口径） |
| 群友触发的回合（含群友转述「主人说……」） | 只能读状态/目录/历史，写请求一律 403 |
| 其它私聊（非主人） | 同上，写一律 403 |
| DSH Web 界面 / 桌宠等非 QQ 会话 | 调不到（工具需要 QQ 会话令牌）；这是有意设计 |
| 本机你本人 | 控制台/命令行审批（`npm run life -- approve ...`） |

其它硬约束：每会话每小时最多 12 次写操作（可配）；所有写操作落 `state/life-settings-audit.jsonl`；
预览计划 15 分钟过期；基础配置文件不会被改写（受管值单独存 sidecar，可随时回滚）。

## 9. 相对参考仓库（surfcore-life）的优化

1. **补上了参考实现最大的缺口**：参考版的 MCP 工具不知道调用者是谁，群里任何人都能让模型改参数；
   本地版把写权限绑到 bridge 的真实 sender 归因（`state/turn-triggers.json` → `ownerTurnAllowed`），
   并复用现有内部模型审批；MCP 进程只做 HTTP 代理，不持有授权逻辑。
2. **不做基础配置双写**：受管值只在 `~/.dsh/surfcore/life-settings.json` 的覆盖层，不改 `config.json`/`bili.config.json`；
   设置页仍可看到基础值（工具 `life_state` 会显示「保存值 / 是否被采用」两层事实，避免 UI≠实现）。
3. **跨午夜窗口**：参考版只接受 `start<end`，本地版接受 `22:00→02:00` 并自动拆成两窗（预览里提示）。
4. **证据写盘节流**：参考版 QQ 每 5 秒写一次证据文件（约 1.7 万次/天），本地改成「变化立即 + 45 秒心跳」。
5. **计划/历史有界**：预览计划保留最近 50 条、历史/观察各上限 1000 条，避免无限增长。
6. **跨进程锁自恢复**：启动/CLI 可识别「死进程遗留锁」并隔离（仍要求人工确认），不会永久卡死。
7. **失败不影响主链路**：sidecar 坏/读失败时消费者保留最后一次成功值，QQ 投递与 B站 tick 不中断。

## 9.5「就在早安一个心跳」——已按你的要求加上（默认开）

你说「每天定时心跳唤醒判断要不要改动，就在早安一个心跳，改完顺便跟我说一声」——已实现并纳入默认配置：

| 项 | 默认 | 说明 |
|---|---|---|
| 开关 | 开 | `config.lifeSettings.dailyReview.enabled=false` 可关 |
| 时间 | `08:00` | `dailyReview.time`，本地时区；错过 3 小时内补跑，DSH 离线/投递失败 10 分钟重试 |
| 频率 | **每天一次** | 同一天绝不反复叫醒；桥上重启/补跑也只补一次；控制台手动试跑不占当天名额 |
| 唤醒位置 | 主人私聊 | 只有主人私聊有写权限；群/别人私聊不跑心跳 |
| 每次最多改 | 2 项 | `dailyReview.maxChanges`（1–5）；提示词要求「没有明确不合适就保持不动，同一参数别来回调」 |
| 流程 | 看状态 → 判断 → 预览 → 执行 → 验证 | `life_state` → `life_preview` → `life_apply` → `life_verify`；不 adopted 不算成功，必要时 `life_rollback` |
| 汇报 | 改完用发送工具说一句 | 「改了什么、为什么、不满意可以让我改回」；没改就不特意发（最多说句早安） |
| 与早安合并 | 自动 | 如果早安问候也开着、对象是主人、时间相同 → 拼成**同一个唤醒**，不再单独排心跳（真正的「一个心跳」） |
| 暂停/非 reserved2 | 跳过并记当天 | 暂停（`socialV2.paused`）或非 reserved2 时不叫醒，避免当天反复重试 |

验收入口（控制台令牌，不经过模型、不占当天名额）：

- `GET /api/life/review` —— 看配置、今天跑没跑、下一次排程；
- `POST /api/life/review/run` —— 立刻手动试跑一次（真实投递到主人私聊）。

> 仍未验证：真实 QQ 上的「08:00 准时+模型自己判断+改完汇报」要上线后看一天；每日 1 次唤醒的 token 成本
> 约等于一次普通轮次（`life_state` 输出很小）。如果你觉得吵，把 `dailyReview.enabled` 关掉即可，不影响手动改参数。
